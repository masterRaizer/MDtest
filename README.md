# cmdq — очередь команд в главный поток игры

Header-only библиотека на C++17 (`include/cmdq/command_queue.hpp`) для приложений,
работающих внутри игры (оверлей, меню, мод, отладочная консоль). Интерфейс живёт в своём
потоке, а игровые данные меняются в главном потоке, поэтому UI не трогает их напрямую:
он отправляет **команды**, а главный поток исполняет их в безопасный момент кадра.

## Как это устроено

```
 UI-поток ─┐  Post(cmd)   ┌──────────────────────┐ exchange(nullptr) ┌──────────────┐
 Сеть   ───┼────CAS──────▶│  lock-free стек      │──────────────────▶│ backlog FIFO │──▶ исполнение
 Консоль ──┘              │  (общий, atomic head)│   раз за кадр     │(только main) │   в главном потоке
                          └──────────────────────┘                   └──────────────┘
```

* **Без мьютексов.** Производитель добавляет команду одной CAS-операцией. Главный поток
  забирает всю накопленную пачку одной `exchange(nullptr)` и разворачивает её в FIFO.
  Потребитель берёт список целиком, поэтому проблемы ABA нет, и главный поток **никогда
  не ждёт** другие потоки.
* **Порядок.** Команды одного потока исполняются в порядке отправки.
* **Кадр не зависает.** Команды, поставленные во время исполнения пачки (в том числе
  самими командами), уходят на следующий кадр.
* **Бюджет времени.** `ExecutePending(1ms)` прекращает работу по истечении бюджета, остаток
  переносится на следующий кадр без потери порядка (минимум одна команда за вызов).
* **Изоляция ошибок.** Исключение из команды не выходит в код игры — оно передаётся в
  `SetErrorHandler`, а остальные команды продолжают исполняться.
* **Без лишней работы в главном потоке.** Аллокация команды (замыкание + узел очереди —
  одна аллокация) происходит в потоке-производителе.

## API

| Метод | Поток | Назначение |
|---|---|---|
| `Post(fn)` | любой | Поставить команду, не блокирует. `false`, если очередь закрыта. |
| `Submit(fn) -> std::future<R>` | любой (кроме главного для `get()`) | Команда с результатом / исключением, например чтение состояния. |
| `Dispatch(fn)` | любой | В главном потоке — выполнить сразу, иначе `Post`. |
| `ExecutePending()` / `ExecutePending(budget)` | главный | Исполнить накопленные команды. |
| `BindToCurrentThread()` | главный | Отметить главный поток (для `Dispatch`). |
| `SetErrorHandler(h)` / `SetWakeHandler(h)` | до старта потоков | Обработка ошибок / пробуждение главного потока. |
| `Close()` | любой | Перестать принимать команды (при выгрузке). |

> `future.get()` из `Submit` нельзя вызывать в главном потоке: команда исполняется именно
> там, получится взаимная блокировка.

## Встраивание

### Вариант 1: вызов в главном цикле / хуке кадра

```cpp
cmdq::CommandQueue g_commands;

// Один раз, из главного потока игры (например, в первом вызове хука).
g_commands.BindToCurrentThread();

// Хук Present / Tick / EndScene — выполняется в главном потоке каждый кадр.
void OnGameFrame() {
    g_commands.ExecutePending(std::chrono::microseconds(500));
    // ... рендер оверлея и т.п.
}

// Поток интерфейса:
void OnHealButton() {
    g_commands.Post([] { Game::LocalPlayer()->SetHealth(100); });
}

void RefreshStats() {
    int gold = g_commands.Submit([] { return Game::LocalPlayer()->Gold(); }).get();
    ui.SetGold(gold);
}
```

### Вариант 2: через обработчик оконных сообщений (Windows)

Если у игры нет удобного хука кадра, можно будить главный поток сообщением.
`SetWakeHandler` вызывается только при переходе очереди из пустой в непустую, поэтому
сообщения не спамятся.

```cpp
constexpr UINT WM_APP_RUN_COMMANDS = WM_APP + 0x42;

g_commands.SetWakeHandler([] { PostMessage(g_gameHwnd, WM_APP_RUN_COMMANDS, 0, 0); });

LRESULT CALLBACK HookedWndProc(HWND h, UINT msg, WPARAM w, LPARAM l) {
    if (msg == WM_APP_RUN_COMMANDS) {
        g_commands.ExecutePending(std::chrono::milliseconds(1));
        if (g_commands.HasPending())  // бюджет кончился — дочистим позже
            PostMessage(h, WM_APP_RUN_COMMANDS, 0, 0);
        return 0;
    }
    return CallWindowProc(g_originalWndProc, h, msg, w, l);
}
```

### Выгрузка

```cpp
g_commands.Close();            // новые команды отклоняются
// ... остановить UI-потоки ...
g_commands.ExecutePending();   // в главном потоке: исполнить оставшееся
```

Неисполненные при разрушении команды освобождаются без вызова; ожидающие `Submit`
получают `std::future_error(broken_promise)` вместо вечного ожидания.

## Ограничения

* `Post` использует `new`; системный аллокатор может кратко брать внутренние блокировки,
  но это происходит в потоке-производителе. Освобождение узла выполняется в главном потоке.
* `SetErrorHandler` и `SetWakeHandler` нужно вызывать до запуска производителей.
* Объекты, захваченные командой по ссылке, должны жить до её исполнения.
