# Система динамической рефлексии C++ (memrefl) — подробная инструкция

Этот документ объясняет, как устроена и как работает библиотека memrefl: от
формата сигнатуры до того, как строка `"Hero.Bag.Items[1].Quantity"`
превращается в адрес в памяти и типизированное значение. Справочник по API
есть и в `README.md`. Здесь объясняется, **почему** всё устроено именно так и
**что происходит внутри**.

## 1. Что это и зачем

memrefl — header-only библиотека на C++17 для анализа данных в памяти
работающего C++-приложения. Её не нужно отдельно собирать: достаточно
подключить заголовки из `include/memrefl`. Библиотека **только читает** память
и ничего в ней не изменяет.

Задача, которую она решает: в памяти программы лежат объекты, но у нас нет её
исходников и заголовков. Нужно уметь сказать «дай значение свойства
`Health` у этого объекта» и получить число, не прописывая вручную адреса,
которые меняются с каждой сборкой программы.

Решение состоит из трёх слоёв, каждый опирается на предыдущий:

```
 Модуль 1: поиск сигнатур           Модуль 2: имена                  Модуль 3: свойства
 ─────────────────────────          ───────────────                  ──────────────────
 "48 8B 05 ?? ?? ?? ?? ..."          ID 0x2A ──▶ "Health"              "Hero.Bag.Items[1].Quantity"
          │                                   ▲                                │
          ▼                                   │                                ▼
 адрес функции / глобальной   ──▶  таблица имён в памяти  ──▶  схема типа + PointerPath ──▶ значение 5
 переменной (не зависит                (массив, хеш-таблица,      (смещения полей, переходы
  от сборки программы)                  словарь известных имён)     по указателям, индексы)
```

* **Модуль 1** находит адреса по «отпечатку» машинного кода. Адрес функции
  или глобальной переменной меняется при каждом обновлении программы, а
  окружающие инструкции обычно остаются теми же.
* **Модуль 2** переводит числовые идентификаторы, которыми программа помечает
  объекты и свойства, в читаемые строки. Источником может быть таблица в
  памяти программы или словарь известных имён. Кодировки (UTF-8, UTF-16,
  Latin-1) приводятся к корректному UTF-8.
* **Модуль 3** даёт доступ к свойствам по строковому пути. Он берёт описание
  типа (заданное вручную или прочитанное из метаданных самой программы),
  превращает путь в цепочку указателей и безопасно читает значение нужного
  типа.

Главный принцип всех трёх модулей: **ничего не падает**. Любой мусорный
указатель, повреждённая таблица или неверный путь дают понятную ошибку, а не
аварийное завершение процесса.

Какие заголовки какие подключают:


Достаточно подключить нужный верхний заголовок, остальные подтянутся сами.

## 3. Как это проверялось

| Платформа | Компилятор | Что сделано |
|---|---|---|
| Linux x86-64 | GCC 13, Clang 18 | Сборка всех целей без предупреждений (`-Wall -Wextra -Wpedantic`), все тесты и примеры |
| Linux x86-64 | GCC 13 + AddressSanitizer, UndefinedBehaviorSanitizer, ThreadSanitizer | Все тесты и примеры без замечаний |
| Windows x64 | MinGW-w64 GCC 13 | Сборка всех целей без предупреждений; тесты и примеры **запущены под Wine 9** (не на настоящей Windows) |
| Windows | MSVC (Visual Studio) | **Не собиралось**: в среде разработки не было MSVC. Код писался с учётом MSVC: интринсики `_BitScanForward`, флаги `/W4 /utf-8`, защита от макросов `min`/`max` из `<windows.h>`. Совместимость с макросами проверена эмуляцией и отдельной целью `windows_macros_check`. **После сборки в Visual Studio обязательно запустите тесты (раздел 4).** |

Под Wine пропускаются две проверки в `data_resolver_tests`: чтение на
границе страницы `PAGE_NOACCESS`. Wine, в отличие от настоящей Windows,
разрешает `ReadProcessMemory` читать такие страницы. На настоящей Windows эти
проверки выполняются.

Кроме того, набор тестов проверен «мутациями»: в код специально вносились
ошибки (сдвиг смещения элемента массива, отсутствие знакового расширения,
потеря унаследованных свойств, `std::min` без скобок), и тесты ловили каждую.

## 4. Сборка и запуск

### 4.1. Требования

* Компилятор C++17: Visual Studio 2019/2022 (MSVC), MinGW-w64 GCC 8+,
  GCC 8+ или Clang 7+ на Linux.
* CMake 3.16+. Он нужен только для примеров и тестов, саму библиотеку
  собирать не нужно.
* Поддерживаемые ОС: Windows и Linux. Поиск в буферах, разбор PE, таблицы
  и схемы работают на любой little-endian платформе, но функции «модули и
  память текущего процесса» есть только для Windows и Linux.

### 4.2. Visual Studio 2022 — через «Открыть папку»

1. Запустите Visual Studio → **Файл → Открыть → Папка…** → выберите
   `G:\система динамической рефлекции C++`.
2. Visual Studio сама найдёт `CMakeLists.txt` и настроит проект. Дождитесь
   строки «Создание CMake завершено» в окне «Вывод».
3. В списке конфигураций вверху выберите **x64-Release** (или x64-Debug).
4. **Сборка → Собрать все**.
5. **Тест → Обозреватель тестов → Запустить все**. Должно быть 5 тестов, все
   зелёные: `signature_scanner_tests`, `signature_scanner_tests_scalar`,
   `data_resolver_tests`, `property_fetcher_tests` и `windows_macros_check`
   (вспомогательная проверка).
6. Примеры запускаются через выпадающий список «Выбрать элемент запуска»
   (например, `property_demo.exe`).

### 4.3. Visual Studio — из командной строки

Откройте **Developer PowerShell for VS 2022** (есть в меню Пуск) и выполните:

### 4.7. Подключение к своему проекту

Библиотека header-only, поэтому её достаточно добавить в пути заголовков:

* **Visual Studio (без CMake)**: Свойства проекта → C/C++ → Общие →
  Дополнительные каталоги включаемых файлов → `G:\система динамической рефлекции C++\include`;
  C/C++ → Язык → Стандарт языка → ISO C++17 (или новее);
  C/C++ → Командная строка → добавьте `/utf-8`. Комментарии в заголовках на
  русском и сохранены в UTF-8; без `/utf-8` MSVC с русской локалью выдаст
  предупреждения C4819.
* **CMake**:
  ```cmake
  add_subdirectory("G:/система динамической рефлекции C++" memrefl)
  target_link_libraries(my_tool PRIVATE memrefl)
  ```
  Цель `memrefl` добавит пути заголовков и библиотеку потоков. Примеры и
  тесты при подключении через `add_subdirectory` не собираются; включить их
  можно опцией `-DMEMREFL_BUILD_EXAMPLES_AND_TESTS=ON`.

В коде подключайте нужный модуль:

```cpp
#include "memrefl/module_regions.hpp"    // модуль 1 (включает signature_scanner.hpp)
#include "memrefl/data_resolver.hpp"     // модуль 2
#include "memrefl/property_fetcher.hpp"  // модуль 3 (включает модуль 2)
```

Заголовки можно подключать и после `<windows.h>`: они не ломаются его
макросами `min`/`max`.

## 5. Основные понятия

| Понятие | Что это |
|---|---|
| **Цель** | Исследуемая программа (процесс) или её снимок (дамп, файл на диске). |
| **Адрес цели** | Число `std::uintptr_t`, адрес в адресном пространстве цели. Все функции принимают и возвращают именно такие адреса. |
| **Регион** (`MemoryRegion`) | Кусок памяти: где его байты лежат **у нас** (`data`), по какому адресу они находятся **в цели** (`base`) и сколько их (`size`). В своём процессе `data == base`. |
| **Снимок** | Копия памяти цели в нашем буфере (после `ReadProcessMemory`, из дампа или файла). Описывается регионом с `data != base`. |
| **Читатель** (`MemoryReader`) | Объект, который читает байты по адресу цели и **сообщает об ошибке**, а не падает. |
| **Сигнатура** (`Pattern`) | Последовательность байтов с масками, например `48 8B 05 ?? ?? ?? ??`. |
| **Якорь** | Самый редкий полностью заданный байт сигнатуры; поиск начинается с него. |
| **ID имени** | Число, которое программа хранит вместо строки (индекс в таблице имён или хеш строки). |
| **Запись строки** | Место в памяти, откуда читается строка: сами символы или структура вида `{указатель, длина}`. |
| **PointerPath** | Цепочка «адрес → прочитать указатель → прибавить смещение → …». |
| **Схема** (`TypeSchema`) | Описание раскладки типа: имя свойства → смещение и тип. |
| **Метаданные рефлексии** | Описания типов, которые хранит сама программа: тип → родитель → список дескрипторов свойств. |
| **Дескриптор свойства** | Запись в метаданных об одном поле: ID имени, смещение, тег типа, вложенный тип. |
| **Тег** | Число в дескрипторе, обозначающее тип поля (например, 1 = int32). |

## 6. Модуль 1 — поиск сигнатур

Файлы: `pattern.hpp`, `signature_scanner.hpp`, `module_regions.hpp`.

### 6.1. Зачем

После перекомпиляции функция `GetRegistry` может переехать с адреса
`0x140012340` на `0x140013F80`, а глобальная переменная `g_Registry` — с
`0x1402A0010` на `0x1402B4410`. Но её код по-прежнему выглядит так:

```
48 8B 05 xx xx xx xx    mov  rax, [rip + g_Registry]   ← xx — смещение, меняется
48 85 C0                test rax, rax                   ← не меняется
74 xx                   jz   short ...                  ← смещение перехода, может меняться
```

Сигнатура `48 8B 05 ?? ?? ?? ?? 48 85 C0 74 ??` описывает именно эту «форму»
и находит функцию в любой сборке, где компилятор породил такой же код.

### 6.2. Формат сигнатуры

| Запись | Смысл |
|---|---|
| `48 8B 05` | Байты в шестнадцатеричном виде через пробел; регистр букв не важен. |
| `?` или `??` | Любой байт. |
| `4?` | Старшая тетрада равна 4, младшая — любая (например, любой REX-префикс `40..4F`). |
| `?F` | Младшая тетрада равна F, старшая — любая. |
| `488B05??` | Слитная запись: строка разбирается парами символов. |
| `Pattern::FromCodeStyle("\x48\x8B\x05\x00", "xxx?")` | Классический формат «байты + маска», `x` — проверять, `?` — любой. |

Пробелы, табуляции и переводы строк между токенами допускаются. Ошибки
сообщаются с позицией: `bad signature token "XY" at offset 6: expected hex
byte pairs (8B), nibble masks (4?) or wildcards (?)`.

Два способа создать сигнатуру:

```cpp
memrefl::Pattern p("48 8B 05 ?? ?? ?? ??");                    // бросит std::invalid_argument при ошибке
auto q = memrefl::Pattern::TryParse(text_from_config, &error);  // вернёт std::nullopt и текст ошибки
```

Пустая сигнатура и сигнатура только из `??` отклоняются: такая «сигнатура»
совпала бы везде.

### 6.3. Внутреннее представление

Каждый байт хранится парой `(value, mask)`, и байт памяти `m` совпадает, если
`(m & mask) == value`:

| Токен | value | mask |
|---|---|---|
| `8B` | `0x8B` | `0xFF` |
| `??` | `0x00` | `0x00` (совпадает всё) |
| `4?` | `0x40` | `0xF0` |
| `?F` | `0x0F` | `0x0F` |

`value` хранится уже с наложенной маской, поэтому при проверке выполняется
одна операция `AND` и одно сравнение на байт, без ветвлений по виду токена.

### 6.4. Якоря

Проверять сигнатуру целиком в каждой позиции памяти дорого. Поэтому заранее
выбираются два **якоря** — самые редкие полностью заданные байты (маска
`0xFF`). Редкость оценивается встроенной таблицей частот байтов в x86/x86-64
коде:

* **очень частые** — `00 FF CC 90 48 8B 89 0F`: нули и −1 в операндах,
  выравнивание `int3`/`nop`, REX.W, `mov`, префикс двухбайтовых опкодов;
* **частые** — прочие REX-префиксы `40 41 44 45 49 4C 4D`, а также
  `24 83 85 8D C0 C3 C7 E8 E9 EB 74 75 33 01 08 10 18 20 28 30 38`;
* **остальные байты** считаются редкими.

Для `48 8B 05 ?? ?? ?? ?? 48 85 C0` якоря — `05` (позиция 2, редкий) и `85`
(позиция 8, частый). Байты `48` и `8B` встречаются в коде почти везде, и
поиск по ним дал бы огромное число ложных кандидатов. При равной частоте
выбирается более ранний байт. Выбор якорей влияет **только на скорость**:
результат поиска от него не зависит, и тесты это проверяют.

### 6.5. Алгоритм поиска

Пусть регион длины `size`, сигнатура длины `n`. Допустимые начала совпадения:
`0 … size − n`, всего `count = size − n + 1` позиций. Порядок выбора способа:

1. **Два якоря и SSE2** (любой x86-64; отключается `-DMEMREFL_NO_SIMD`):

   ```
   позиции начала:     i   i+1  i+2 ...  i+15
   байты якоря 1:  data[i+a1 ... i+a1+15]  ──pcmpeqb с v1──▶  маска 16 байт
   байты якоря 2:  data[i+a2 ... i+a2+15]  ──pcmpeqb с v2──▶  маска 16 байт
                                                         AND ──▶ pmovmskb ──▶ 16 бит
   бит k = 1  ⇔  в позиции i+k совпали оба якоря  ⇔  кандидат
   ```

   За одну итерацию обрабатываются 4 таких блока, то есть 64 позиции. Если ни
   в одном блоке нет кандидатов (а в реальном коде так почти всегда), на всё
   уходит одна проверка «всё по нулям». Каждый кандидат проверяется целиком.
   Блок читается, только если `i + 16 <= count`. Тогда самое дальнее чтение
   `i + 15 + якорь` гарантированно внутри региона, потому что якорь меньше `n`.
   Последние позиции (меньше 16) проверяются по одной.

2. **Один якорь или нет SSE2** (например, ARM): `memchr` ищет байт якоря в
   диапазоне `[a, a + count)`. Это функция стандартной библиотеки, она уже
   векторизована. Каждая находка — кандидат с началом `находка − a`.

3. **Нет ни одного полностью заданного байта** (только маски вида `4?`):
   проверяется каждая позиция.

Совпадения могут перекрываться: `AB AB` в `AB AB AB` даёт две позиции. Они
выдаются в порядке возрастания адреса.

### 6.6. Регионы и их склейка

```cpp
struct MemoryRegion {
  std::uintptr_t base;        // адрес data[0] в цели
  const std::uint8_t* data;   // где байты лежат у нас
  std::size_t size;
  static MemoryRegion InProcess(const void* address, std::size_t size);           // data == base
  static MemoryRegion Snapshot(const void* copy, std::size_t size, std::uintptr_t remote_base);
};
```

Сканер и читатель памяти нормализуют список регионов (`NormalizeRegions`):

* пустые регионы отбрасываются;
* регионы сортируются по адресу;
* соседние регионы склеиваются, если они смежны **и** в цели, **и** у нас в
  памяти. Поэтому сигнатура, лежащая на границе двух регионов, тоже
  находится.

Регионы не должны перекрываться.

### 6.7. Откуда брать регионы

**Модуль текущего процесса** (`module_regions.hpp`):

```cpp
auto scanner = memrefl::ScannerForModule("app.exe");                          // только код
auto everything = memrefl::ScannerForModule("app.exe", memrefl::SectionFilter::All);  // код и данные
auto self = memrefl::ScannerForModule();                                      // "" — главный exe
```

* **Windows.** Модуль ищется через `GetModuleHandleW`; имя переводится из UTF-8
  в UTF-16. Читаемый размер заголовков узнаётся у `VirtualQuery`, а не из
  полей заголовка. Затем разбираются PE-заголовки. Для каждой нужной секции
  через `VirtualQuery` отбираются только реально читаемые страницы
  (`MEM_COMMIT`, без `PAGE_NOACCESS` и `PAGE_GUARD`). Упаковщики и защитники
  меняют права страниц после загрузки, и без этой проверки сканер мог бы
  уронить процесс.
* **Linux.** Используется `dl_iterate_phdr`, берутся сегменты `PT_LOAD` с
  флагом `PF_R`, а для `SectionFilter::Code` ещё и с `PF_X`. Главная
  программа — первая запись; её имя берётся из `/proc/self/exe`. Модуль можно
  указать по имени файла (`libc.so.6`) или полному пути.
* Модуль не найден — сканер пуст (`empty() == true`) и ничего не находит.

**PE-файл в буфере** (на любой ОС):

```cpp
// Файл с диска: адреса как в IDA/Ghidra (ImageBase + RVA).
memrefl::SignatureScanner s(memrefl::PeImageRegions(file.data(), file.size(), memrefl::PeLayout::File));

// Дамп загруженного модуля из другого процесса: укажите реальную базу (ASLR).
memrefl::SignatureScanner d(memrefl::PeImageRegions(dump.data(), dump.size(), memrefl::PeLayout::Mapped,
                                                    memrefl::SectionFilter::Code, remote_base));
```

Разница между раскладками:

| | Где секция в буфере | Сколько байтов |
|---|---|---|
| `PeLayout::File` | `PointerToRawData` | `min(VirtualSize, SizeOfRawData)`: хвост — выравнивание, а `.bss` в файле отсутствует |
| `PeLayout::Mapped` | `VirtualAddress` (RVA) | `VirtualSize` (или `SizeOfRawData`, если линкер оставил 0) |

`ParsePeHeaders` читает заголовки PE32 и PE32+ **с проверкой каждой границы**
(смещения считаются в 64 битах, чтобы сумма не переполнилась):

1. `MZ` по смещению 0, затем `e_lfanew` по смещению `0x3C`;
2. `PE\0\0` по `e_lfanew`;
3. `IMAGE_FILE_HEADER`: число секций (+2), размер optional header (+16);
4. optional header: Magic `0x10B` (PE32, ImageBase по +28, 4 байта) или `0x20B`
   (PE32+, ImageBase по +24, 8 байт); `SizeOfImage` (+56) и `SizeOfHeaders`
   (+60) — в обоих форматах на одном месте;
5. таблица секций по 40 байт: имя, `VirtualSize`, `VirtualAddress`,
   `SizeOfRawData`, `PointerToRawData`, `Characteristics`.

Повреждённые заголовки дают `std::nullopt`, а не чтение за границей буфера.
Секция, выходящая за конец буфера, усекается.

**Память другого процесса.** Узнайте базу и размер модуля, например через
`CreateToolhelp32Snapshot` + `Module32FirstW`/`Module32NextW`. Прочитайте
модуль постранично (`ReadProcessMemory`; страницы, которые не читаются,
пропустите или заполните нулями) и разберите буфер как `PeLayout::Mapped` с
`remote_base`. Найденные адреса будут адресами в том процессе.

### 6.8. От совпадения к адресу

Совпадение — это адрес **инструкции**. Чаще всего нужен адрес, на который
она ссылается. В x86-64 такие ссылки относительные: 32-битное знаковое
смещение отсчитывается от **конца** инструкции:

```
цель = адрес_инструкции + длина_инструкции + disp32
```

| Инструкция | Байты | `ResolveRelative(addr, disp_offset, size)` |
|---|---|---|
| `call func` | `E8 rel32` | `(addr, 1, 5)` |
| `jmp func` | `E9 rel32` | `(addr, 1, 5)` |
| `mov rax, [rip+g]` | `48 8B 05 disp32` | `(addr, 3, 7)` |
| `lea rcx, [rip+g]` | `48 8D 0D disp32` | `(addr, 3, 7)` |
| `mov eax, [rip+g]` (без REX) | `8B 05 disp32` | `(addr, 2, 6)` |

`disp32` читается не из памяти цели напрямую, а через регионы сканера. Поэтому
это работает и для снимков, у которых `data != base`.

Обычный рецепт «найти глобальную переменную» объединяет оба шага в один вызов:

```cpp
auto g_registry = scanner.FindRelativeTarget(memrefl::Pattern("48 8B 05 ?? ?? ?? ?? 48 85 C0 74 ??"), 3, 7);
```

Он возвращает `nullopt`, если сигнатура не нашлась или нашлась больше одного
раза.

### 6.9. Как составить хорошую сигнатуру

1. **Маскируйте всё, что зависит от расположения:** `rel32` у `call/jmp`,
   `disp32` у `[rip+…]`, короткие смещения переходов (`74 ??`), а также
   непосредственные значения, похожие на адреса или размеры структур, если
   они могут меняться.
2. **Оставляйте опкоды и регистры** (`48 8B 05`, `48 85 C0`): компилятор
   меняет их, только если меняется сам код.
3. **Длина** — обычно 10–30 байт. Слишком короткая сигнатура неуникальна,
   слишком длинная захватывает изменчивые соседние инструкции.
4. **Проверьте уникальность**: `scanner.FindAll(p, 2).size() == 1`. В коде
   используйте `FindUnique`: если после обновления сигнатура начала находить
   два места, лучше получить «не найдено», чем неверный адрес.
5. **Проверьте на двух сборках программы**, если они доступны. Офлайн это
   удобно делать через `PeImageRegions(..., PeLayout::File)`.
6. Если у самой функции нет уникального начала, ищите **место её вызова**
   (`E8 ?? ?? ?? ?? 48 8B D8`) и берите цель `call` через
   `ResolveRelative(hit, 1, 5)`.

### 6.10. Производительность

Замеры `examples/scan_benchmark.cpp`: 64 МБ реального машинного кода, один
поток, GCC 13 `-O2`. Сканер работает со скоростью около 6 ГБ/с, в 5–11 раз
быстрее наивного перебора. На таком объёме скорость упирается в пропускную
способность памяти: если данные помещаются в кеш (256 КБ), фильтр выдаёт
22–26 ГБ/с. Поиск одной сигнатуры в модуле размером в десятки мегабайт
занимает единицы миллисекунд.

## 7. Модуль 2 — Generic Data Resolver

Файлы: `memory_reader.hpp`, `text.hpp`, `name_table.hpp`, `data_resolver.hpp`.

### 7.1. Задача

Программа хранит у объекта не строку `"Camera"`, а число: индекс в таблице
имён, хеш строки или упакованное значение с флагами. Resolver переводит
такие числа в строки:

```
 ID из памяти ──KeyConverter──▶ LookupKey{value, hash} ──NameTable──▶ запись строки ──StringFormat──▶ UTF-8
   0x0000000B    BitField(1)        {5, 5}                 массив[5]      {char16_t*, len}     "Камера"
```

Все звенья настраиваются независимо. Раскладки описываются данными
(структуры `*Spec`), без наследования и перекомпиляции.

### 7.2. Чтение памяти

`MemoryReader` — интерфейс с одним виртуальным методом:

```cpp
virtual bool ReadBytes(std::uintptr_t address, void* out, std::size_t size) const = 0;
```

Метод возвращает `false`, если хоть один байт недоступен. Поверх него
определены `Read<T>(addr)`, `ReadUnsigned(addr, 1..8)` и
`ReadPointer(addr, pointer_size)`, возвращающие `std::optional`.
`pointer_size` позволяет 64-битному инструменту читать 32-битную цель
(указатели по 4 байта).

| Читатель | Как работает |
|---|---|
| `ProcessMemoryReader::Self()` | Свой процесс, но **через ядро**: `ReadProcessMemory(GetCurrentProcess(), …)` на Windows и `process_vm_readv(getpid(), …)` на Linux. Невалидный адрес даёт ошибку или частичное чтение, а не исключение доступа (SIGSEGV). Цена — системный вызов на каждое чтение. |
| `ProcessMemoryReader(HANDLE)` (Windows) | Другой процесс. Нужен handle с правом `PROCESS_VM_READ`: `OpenProcess(PROCESS_VM_READ \| PROCESS_QUERY_LIMITED_INFORMATION, FALSE, pid)`. Handle не закрывается читателем. |
| `ProcessMemoryReader(pid)` (Linux) | Другой процесс. Нужен ptrace-доступ: тот же пользователь и `kernel.yama.ptrace_scope` = 0, либо `CAP_SYS_PTRACE`. |
| `RegionReader(regions)` | Снимки и дампы. Буферы не копируются, и изменения в них видны сразу. Используется в тестах. |
| свой класс | Унаследуйтесь от `MemoryReader`, например для чтения по сети или из файла ядра. |

Все читатели без состояния, их можно использовать из нескольких потоков.

### 7.3. PointerPath

`PointerPath` — адрес, заданный цепочкой указателей. Перед **каждым**
смещением читается указатель по текущему адресу:

```
PointerPath(base)               → base
PointerPath(base, {0})          → *base
PointerPath(base, {0x10})       → *base + 0x10
PointerPath(base, {0x10, 0x8})  → *(*base + 0x10) + 0x8
```

Пример: глобальная переменная `Registry* g_Registry` по адресу `G`, а в
`Registry` лежит `{const char** names; uint32 count}`:

* адрес массива имён — `*(*G + 0)` → `PointerPath(G, {0, 0})`;
* адрес поля count — `*G + 8` → `PointerPath(G, {8})`.

Важное свойство: путь **разрешается при каждом обращении**. Если программа
перевыделит массив (он вырос) или пересоздаст объект, следующее чтение пойдёт
по новому адресу, а не в освобождённую память.

Что ещё умеет:

* `Resolve(reader, pointer_size)` → `std::optional<адрес>`; нулевой указатель
  на любом шаге — `nullopt`;
* `ResolveTraced(...)` → дополнительно номер шага, на котором оборвалась
  цепочка, и причина: нулевой указатель или недоступная память;
* `Offset(delta)` и `Dereference()` — построение пути по шагам
  (их использует модуль 3);
* `ToString()` → `"[[0x1000]+0x10]+0x8"`: квадратные скобки означают «прочитать указатель».

### 7.4. Строки в памяти: StringFormat

Таблица находит адрес **записи**, а `StringFormat` говорит, как прочитать из
неё строку:

| Поле | По умолчанию | Смысл |
|---|---|---|
| `encoding` | `Utf8` | `Utf8`, `Utf16LE` или `Latin1` |
| `chars_offset` | 0 | Где символы относительно записи… |
| `chars_by_pointer` | `false` | …прямо там (`false`) или по указателю, лежащему там (`true`) |
| `pointer_size` | `sizeof(void*)` | Ширина этого указателя в цели |
| `length_size` | 0 | 0 — строка до нулевого символа; 1/2/4/8 — поле длины такого размера |
| `length_offset` | 0 | Где поле длины относительно записи |
| `length_shift`, `length_mask` | 0, все биты | Длина = `(поле >> shift) & mask` (если длина упакована с флагами) |
| `utf16_flag_mask` | 0 | Если этот бит поля длины установлен — строка в UTF-16LE, иначе в `encoding` |
| `max_chars` | 1024 | Строка длиннее считается мусором |

Типичные раскладки:

| В памяти | Настройка |
|---|---|
| `const char*` или `char[]` с нулём в конце | по умолчанию |
| `const wchar_t*` (Windows) с нулём | `encoding = Utf16LE` |
| `{uint16 len; char chars[]}` | `length_size = 2`, `chars_offset = 2` |
| `{const char16_t* data; int32 length}` (длина может включать `\0`) | `chars_by_pointer = true`, `length_offset = 8`, `length_size = 4`, `encoding = Utf16LE` |
| `uint16 header`: бит 0 — «широкая» строка, длина в битах 6..15 | `length_size = 2`, `length_shift = 6`, `utf16_flag_mask = 1`, `chars_offset = 2`, `encoding = Latin1` |
| что-то особенное | свой `StringDecoder` — функция `(reader, адрес записи) → optional<string>` |

Как `ReadString` читает строку:

1. Если задано поле длины, читается длина (с учётом shift, mask и флага
   UTF-16). Длина больше `max_chars` — ошибка. Затем читается ровно
   `длина × размер символа` байт, и завершающие нулевые символы отбрасываются.
2. Если поля длины нет, символы читаются **блоками до 256 байт, которые не
   пересекают границу 4-КБ страницы**. Страница доступна либо целиком, либо
   никак, поэтому строка, кончающаяся в самом конце последней доступной
   страницы, читается без ошибки: блок не задевает следующую, недоступную
   страницу. Если блок всё же не прочитался (например, конец снимка не
   выровнен по странице), строка дочитывается по одному символу. Строка без
   нуля в пределах `max_chars` — ошибка.
3. `{nullptr, 0}` — пустая строка; `{nullptr, n > 0}` — ошибка.
4. Байты переводятся в корректный UTF-8 (следующий раздел).

### 7.5. Кодировки

Внутри библиотеки все имена — **корректный UTF-8**. Что бы ни лежало в
памяти, в вывод (консоль, CSV, JSON) не попадёт невалидная последовательность.

**UTF-8 проверяется строго**, по таблице 3-7 стандарта Unicode:

| Первый байт | Второй байт | Дальше | Что отсекается |
|---|---|---|---|
| `00..7F` | — | — | |
| `C2..DF` | `80..BF` | — | `C0`, `C1` — overlong-формы |
| `E0` | `A0..BF` | `80..BF` | overlong |
| `E1..EC`, `EE..EF` | `80..BF` | `80..BF` | |
| `ED` | `80..9F` | `80..BF` | суррогаты `D800..DFFF` |
| `F0` | `90..BF` | `80..BF` ×2 | overlong |
| `F1..F3` | `80..BF` | `80..BF` ×2 | |
| `F4` | `80..8F` | `80..BF` ×2 | значения больше `U+10FFFF` |

Некорректная последовательность заменяется на **U+FFFD (�) по правилу
«максимальной части»**, как в браузерах и ICU. Один символ замены ставится на
самое длинное начало корректной последовательности, которое оборвалось:

* `C0 80` → `��`: `C0` не может начинать символ, `80` — тоже;
* `E2 82` в конце строки → `�`: обрыв трёхбайтового символа «€»;
* `a E2 82 b` → `a�b`;
* `ED A0 80` → `���`: суррогат в UTF-8 запрещён, `A0` не подходит после `ED`.

**UTF-16LE**: суррогатные пары `D800..DBFF` + `DC00..DFFF` собираются в один
символ (например, 😀). Одиночный суррогат заменяется на U+FFFD. Если у буфера
нечётная длина, последний байт отбрасывается.

**Latin-1** (ISO-8859-1, «ANSI»): байт = кодовая точка `U+0000..U+00FF`;
`E9` → `é`.

Обратные преобразования: `Utf8ToUtf16`, `Utf8ToWide` (для Windows API).
`std::codecvt` не используется: в C++17 он объявлен устаревшим.

### 7.6. Хеши

Если ID объекта — это хеш его имени, а самой таблицы в памяти нет, можно
посчитать хеши известных имён так же, как это делает программа, и построить
обратный словарь. Поддерживаются алгоритмы:

| `HashAlgorithm` | Описание | Контрольное значение |
|---|---|---|
| `Fnv1_32` | FNV-1, 32 бита | `"a"` → `0x050C5D7E` |
| `Fnv1a32` | FNV-1a, 32 бита | `"a"` → `0xE40C292C` |
| `Fnv1a64` | FNV-1a, 64 бита | `"a"` → `0xAF63DC4C8601EC8C` |
| `Crc32` | IEEE 802.3 (как в zlib/PNG) | `"123456789"` → `0xCBF43926` |

`StringHashOptions` описывает, как программа хеширует имя: `algorithm`,
`input` (байты строки в UTF-8, UTF-16LE или Latin-1) и `ascii_lowercase`
(приводить ли латиницу к нижнему регистру: `"Player"` == `"player"`).

### 7.7. Ключ и конвертер

`LookupKey{value, hash}`:

* `value` — индекс для массива; ключ для сравнения в хеш-таблице и словаре;
* `hash` — по нему хеш-таблица выбирает корзину.

`KeyConverter` превращает сырой ID в ключ:

| Конвертер | Когда | Результат |
|---|---|---|
| `Direct()` (по умолчанию) | ID — индекс или уже хеш имени | `value = hash = id` |
| `BitField(shift, mask, bias)` | индекс упакован с флагами; нумерация с 1 | `value = hash = ((id >> shift) & mask) + bias` |
| `HashedId(algorithm, bytes)` | хеш-таблица хеширует числовой ключ перед выбором корзины | `value = id`, `hash = H(младшие bytes байт id)` |
| `Custom(fn)` | своя логика; `nullopt` — «у этого ID имени нет» | что вернёт `fn` |
| `a.Then(b)` | композиция | `b` получает `value` от `a` как ID |

Примеры:

* `BitField(0, 0xFFFFFFFF)`: индекс в младших 32 битах, выше — номер экземпляра;
* `BitField(1, ~0ull)`: младший бит — флаг;
* `BitField(0, ~0ull, -1)`: нумерация с единицы. ID 0 превращается в
  огромный индекс, заведомо за пределами массива, то есть «нет имени».

### 7.8. Таблицы имён

**`ArrayNameTable` (`ArrayTableSpec`)** — массив в памяти цели, ключ = индекс.

```
плоский:      element = array + index × element_size
поблочный:    chunk   = *(array + (index / chunk_capacity) × pointer_size)
              element = chunk + (index % chunk_capacity) × element_size
запись:       element_is_pointer ? *(element + element_offset) : element + element_offset
```

| Поле | Смысл |
|---|---|
| `array` (`PointerPath`) | Начало массива (или массива указателей на блоки); перечитывается при каждом обращении |
| `pointer_size` | Ширина указателей цели |
| `element_is_pointer`, `element_size`, `element_offset` | Элемент — указатель на запись или сама запись; шаг (0 = `pointer_size`); где указатель или запись внутри элемента (например, массив структур `{id, name*}`) |
| `chunk_capacity` | > 0 — поблочный массив (таблицы, растущие без перевыделения) |
| `count`, `count_field` + `count_size`, `max_count` | Число элементов: известное, из поля в памяти (перечитывается) или не ограничено. Верхняя граница — `max_count` (по умолчанию 2²⁴) |
| `string` / `decoder` | Как читать запись |

Нулевой элемент — пустой слот («нет имени»). Если длина массива неизвестна,
перебор (`ForEach`) идёт до первого нечитаемого элемента.

**`HashNameTable` (`HashTableSpec`)** — хеш-таблица в памяти цели.

```
корзина = Modulo ? hash % bucket_count : hash & (bucket_count − 1)

Chained:        node = *(buckets + корзина × pointer_size)
                пока node ≠ 0: если key(node) == value → запись; node = *(node + next_offset)

LinearProbing:  slot = buckets + ((корзина + k) % bucket_count) × slot_size, k = 0, 1, 2…
                key == empty_key   → нет (дальше искать бессмысленно)
                key == deleted_key → пропустить («надгробие» удалённого элемента)
                key == value       → запись
```

Ключ сравнивается по `key_size` байтам, и `value` обрезается до той же
ширины. `Mask` требует, чтобы `bucket_count` было степенью двойки, иначе это
ошибка конфигурации и результат — «не найдено». Длина цепочки и число проб
ограничены `max_chain` (4096): зацикленная цепочка в повреждённой памяти не
повесит поиск.

**`DictionaryNameTable` (`DictionarySpec`)** — локальный словарь «ключ → имя».
`Add(name)` вычисляет ключ как хеш имени (`StringHashOptions`), а
`Add(key, name)` добавляет явную пару. При коллизии (тот же ключ, другое имя)
остаётся первое имя, а коллизия записывается в `collisions()`.

**`FallbackNameTable`** — цепочка таблиц: первая нашедшая имя побеждает.
Например, сначала живая таблица процесса, затем словарь известных имён.

**Своя таблица** — унаследуйтесь от `NameTable` и реализуйте
`Lookup(const LookupKey&)` и, при желании, `ForEach`.

### 7.9. GenericDataResolver

Тип маппинга выбирается спецификацией:

```cpp
using MappingSpec = std::variant<ArrayTableSpec, HashTableSpec, DictionarySpec>;
memrefl::GenericDataResolver r(reader, spec, converter, options);   // таблица создаётся по spec
memrefl::GenericDataResolver r2(std::make_shared<MyTable>(...));    // или готовая NameTable
```

Что происходит при `Resolve(id)`:

1. Ищем `id` в кеше; нашли — возвращаем.
2. `converter(id)`. Вернул `nullopt` — ID отклонён (это учитывается в `stats().rejected`).
3. `table.Lookup(key)`. Память читается **без блокировки**: два потока могут
   прочитать одно имя одновременно, зато никто не ждёт чужого медленного
   чтения.
4. Результат кладётся в кеш по правилам:
   * найденные имена кешируются (`cache_hits = true`);
   * промахи по умолчанию **не** кешируются (`cache_misses = false`): в живом
     процессе имя может появиться позже. Для неизменного снимка кеширование
     промахов экономит чтения;
   * при `max_cache_entries` (2²⁰) кеш очищается целиком.

Кеш защищён `std::mutex`, а не `std::shared_mutex`. Под блокировкой
выполняются только поиск в хеш-таблице и копирование строки. Кроме того, в
сборке MinGW под Wine 4-поточный тест с `std::shared_mutex` изредка получал
«не найдено» для известных ID (2 из 12 запусков), а тот же шаблон доступа без
memrefl вообще зависал. С `std::mutex` тест прошёл 15 запусков из 15.

Остальное:

| Метод | Назначение |
|---|---|
| `Label(id)`, `Labels(ids)` | Всегда строка: имя или `<unknown:0x1A2B>` (формат меняется через `ResolverOptions::fallback_label`) |
| `ForEachName(visitor)` | Выгрузить всю таблицу; ключи — ключи таблицы, а не исходные ID |
| `ExportDictionary()` | Снимок таблицы в локальный словарь: имена доступны и после завершения процесса |
| `stats()` | `lookups = cache_hits + resolved + unresolved`, отдельно `rejected` |
| `ClearCache()` | Сброс кеша |

`Resolve` можно вызывать из нескольких потоков. `GenericDataResolver` можно
перемещать (например, хранить в `std::vector`).

### 7.10. Пример

```cpp
auto reader = std::make_shared<memrefl::ProcessMemoryReader>(memrefl::ProcessMemoryReader::Self());

// Типы: g_TypeRegistry -> {const char** names; uint32 count}; ID = (индекс << 1) | флаг.
memrefl::ArrayTableSpec types;
types.array = memrefl::PointerPath(type_registry_address, {0, 0});   // *(*g_TypeRegistry).names
types.count_field = memrefl::PointerPath(type_registry_address, {8});  // &(*g_TypeRegistry).count
memrefl::GenericDataResolver type_names(reader, types, memrefl::KeyConverter::BitField(1, ~0ull));

// Свойства: ID = CRC32 имени в нижнем регистре; таблицы нет, есть список имён.
memrefl::DictionarySpec known;
known.hashing = {memrefl::HashAlgorithm::Crc32, memrefl::Encoding::Utf8, /*ascii_lowercase=*/true};
known.names = {"Health", "MaxSpeed"};
memrefl::GenericDataResolver property_names(nullptr, known);

std::string label = type_names.Label(object_type_id);   // "Camera" или "<unknown:0x13>"
```

## 8. Модуль 3 — PropertyFetcher

Файлы: `property_schema.hpp`, `reflection_loader.hpp`, `property_fetcher.hpp`.

### 8.1. Задача

```cpp
fetcher.Get<int>(hero, "Health");                                   // Result<int>
fetcher.Get<std::string>(world, "Hero.Bag.Items[1].DisplayName");  // Result<std::string>
```

Пользователь называет свойство строкой, а система:

1. определяет тип объекта и находит свойство в схеме; имена разрешаются
   через `GenericDataResolver`;
2. строит `PointerPath` от объекта до значения и проходит по нему;
3. читает значение нужного типа с проверками и возвращает `Result<T>`.

### 8.2. Типы свойств и значения

| `PropertyType` | Как читается | Значение (`PropertyValue`) |
|---|---|---|
| `Bool` | 1 байт, `(байт & bool_mask) != 0` (`bool_mask` для битовых полей) | `bool` |
| `Int8`, `Int16`, `Int32`, `Int64` | 1/2/4/8 байт со **знаковым расширением** (`-3` в int16 → −3) | `std::int64_t` |
| `UInt8` … `UInt64` | 1/2/4/8 байт | `std::uint64_t` |
| `Float`, `Double` | 4/8 байт | `double` |
| `Pointer` | указатель шириной `pointer_size` | `Address` |
| `String` | `ReadString` по `StringFormat` свойства | `std::string` (UTF-8) |
| `Name` | ID шириной `name_id_size`, затем resolver | `std::string` |
| `Struct` | — (структура лежит прямо в объекте) | `Address` начала структуры |
| `StructPointer` | указатель на объект | `Address` |
| `Array` | inline — адрес первого элемента; dynamic — указатель на данные | `Address` |
| `Unknown` | не читается (тип не распознан в метаданных) | ошибка `UnsupportedType` |

`PropertyValue = std::variant<bool, std::int64_t, std::uint64_t, double, std::string, Address>`.
`FormatValue(value)` превращает значение в текст для отчёта: `true`, `-5`,
`12.5`, строку как есть, адрес как `0x1A2B`.

### 8.3. Статические схемы

```cpp
auto schemas = std::make_shared<memrefl::SchemaRegistry>();
schemas->Add(memrefl::TypeSchema("Actor")
                 .Add("Id", memrefl::PropertyType::UInt32, 0x00)
                 .Add(memrefl::BoolProperty("IsActive", 0x04, /*mask=*/0x01)));
schemas->Add(memrefl::TypeSchema("Character", /*parent=*/"Actor")
                 .Add("Health", memrefl::PropertyType::Int32, 0x10)
                 .Add("Defense", memrefl::PropertyType::Float, 0x14)
                 .Add(memrefl::NameProperty("Class", 0x1C))                       // ID -> строка
                 .Add(memrefl::StructProperty("Stats", 0x50, "Stats"))            // структура по значению
                 .Add(memrefl::ObjectProperty("Inventory", 0x68, "Inventory")));  // указатель
```

Помощники для описаний свойств:

| Функция | Что создаёт |
|---|---|
| `ScalarProperty(name, type, offset)` | Любое скалярное свойство (то же, что `TypeSchema::Add(name, type, offset)`) |
| `BoolProperty(name, offset, mask)` | `bool`, в том числе бит в байте |
| `StringProperty(name, offset, format)` | Строка (формат — `StringFormat` из модуля 2) |
| `NameProperty(name, offset, id_size, resolver_key)` | ID имени → строка; `resolver_key` выбирает resolver, зарегистрированный в fetcher'е |
| `StructProperty(name, offset, type)` | Вложенная структура по значению |
| `ObjectProperty(name, offset, type)` | Указатель на объект; без `type` тип определяется по самому объекту (нужна рефлексия) |
| `InlineArrayProperty(name, offset, element, count, stride)` | Массив прямо в объекте |
| `DynamicArrayProperty(name, offset, element, count_offset, count_size, stride)` | Контейнер `{T* data; …; count}`: данные — первое поле, длина — по `count_offset` от начала контейнера |

Для массивов структур или строк задайте у описания `struct_type` (имя схемы
элемента) или `string` (формат элемента): поля массива относятся к его
элементам. Если у элементов нет фиксированного скалярного размера, `stride`
обязателен.

Полный набор полей `PropertyDesc`: `name`, `type`, `offset`, `bool_mask`,
`string`, `name_resolver`, `name_id_size`, `struct_type`,
`struct_type_object` (адрес типа в метаданных) и `array` (`ArrayLayout`:
`element`, `stride`, `dynamic`, `inline_count`, `count_offset`, `count_size`,
`max_count`).

**Наследование.** У схемы может быть родитель (одиночное наследование).
Свойство ищется сначала в самом типе, затем в родителе и так далее. Цикл в
описаниях (A → B → A) обрывается: глубина ограничена 64, повторы
отсекаются. Повторное имя свойства или типа — исключение
`std::invalid_argument` при создании схемы.

### 8.4. Схемы из метаданных рефлексии программы

Многие программы хранят описания своих типов в памяти. Обобщённая картина,
которую понимает `ReflectionLoader`:

```
 объект                    тип (TypeInfo)                    дескриптор свойства (PropInfo)
 ┌──────────────┐          ┌───────────────────┐             ┌──────────────────────────┐
 │ type* ───────┼────────▶ │ name_id           │      ┌────▶ │ name_id                  │
 │ ...поля...   │          │ super* ──▶ родитель│      │      │ offset (смещение поля)   │
 └──────────────┘          │ properties ───────┼──────┘      │ tag (тип поля)           │
  object_type_offset       └───────────────────┘             │ inner* ──▶ тип структуры │
                            type_name_offset                 │ next* ──▶ следующий      │
                            super_offset                     └──────────────────────────┘
                            list_offset                       property_*_offset, next_offset
```

`ReflectionLayout` описывает, где что лежит:

| Поле | По умолчанию | Смысл |
|---|---|---|
| `pointer_size` | `sizeof(void*)` | Ширина указателей цели |
| `object_type_offset` | 0 | Где в объекте указатель на его тип |
| `type_name_offset`, `type_name_size` | 0, 4 | ID имени типа |
| `super_offset` | нет | Указатель на родительский тип |
| `list_kind` | `LinkedList` | `LinkedList`: тип хранит указатель на первый дескриптор, дескриптор — на следующий. `PointerArray`: тип хранит `{PropInfo** data; count}` |
| `list_offset` | 0 | Первый дескриптор или массив указателей |
| `list_count_offset`, `list_count_size` | 0, 4 | Число дескрипторов (`PointerArray`) |
| `next_offset` | 0 | Следующий дескриптор (`LinkedList`) |
| `property_name_offset`, `property_name_size` | 0, 4 | ID имени свойства |
| `property_offset_offset`, `property_offset_size` | 0, 4 | Смещение поля в объекте |
| `property_tag_offset`, `property_tag_size` | 0, 4 | Тег типа поля |
| `property_inner_type_offset` | нет | Указатель на тип вложенной структуры, объекта или элементов |
| `tags` | пусто | Тег → прототип `PropertyDesc` (тип, формат строки, раскладка массива) |
| `classify` | нет | Своя функция `(reader, адрес дескриптора) → optional<PropertyDesc>` вместо `tags` |
| `max_properties`, `max_depth` | 4096, 64 | Защита от мусора |

Как `ReflectionLoader::Load(type)` строит схему:

1. **Цепочка родителей.** Тип → `super` → `super` …, пока указатель не
   станет нулевым. Повторный тип (цикл) обрывает цепочку. Длина ограничена
   `max_depth`.
2. **Дескрипторы.** Для каждого типа цепочки, **начиная с самого базового**,
   читается список дескрипторов: связный список (цикл в нём обрывается) или
   массив указателей (`count` больше `max_properties` — ошибка; нулевые
   элементы пропускаются).
3. **Каждый дескриптор:**
   * по `tags[тег]` (или `classify`) берётся прототип описания, а
     неизвестный тег даёт тип `Unknown`;
   * имя — `GenericDataResolver::Label(ID)`, то есть неразрешённое имя
     становится `<unknown:0x…>` и всё равно доступно по этой подписи;
   * смещение берётся из дескриптора;
   * `struct_type_object` — из поля вложенного типа.
4. **Переопределение.** Свойство потомка с тем же именем заменяет
   родительское на его месте. В итоговой схеме родительские свойства идут
   первыми.
5. Имя схемы — разрешённое имя типа. Схема **кешируется по адресу типа**
   (`ClearCache()` сбрасывает кеш). `Load` потокобезопасен.

Любая нечитаемая часть метаданных даёт ошибку `UnreadableMemory` с адресом,
а не частично собранную схему.

Пример тегов:

```cpp
layout.tags[1] = memrefl::ScalarProperty("", memrefl::PropertyType::Int32, 0);
layout.tags[2] = memrefl::ScalarProperty("", memrefl::PropertyType::Float, 0);
layout.tags[3] = memrefl::ObjectProperty("", 0);  // тип объекта — по самому объекту
layout.tags[4] = memrefl::DynamicArrayProperty("", 0, memrefl::PropertyType::StructPointer, 8);
layout.tags[5] = memrefl::NameProperty("", 0);
```

Имя и смещение в прототипах не важны: загрузчик заполнит их из дескриптора.

`classify` нужен, когда тег устроен сложнее. Например, тег может быть
указателем на «класс свойства» со своим именем: прочитайте его, разрешите
имя и верните подходящий `PropertyDesc`.

### 8.5. Синтаксис пути

```
путь     = сегмент { "." сегмент }
сегмент  = имя [ "[" индекс "]" ]
имя      = любые символы, кроме  .  [  ]   (пробелы допустимы: "Display Name")
индекс   = десятичное число
```

Корректные пути: `Health`, `Stats.Resist[2]`, `Inventory.Items[1].Name`.
Ошибки синтаксиса: `""`, `A..B`, `A.`, `[1]`, `A[x]`, `A[1][2]` (массивы
массивов не поддерживаются), слишком большой индекс. Каждая ошибка
сообщается с позицией.

### 8.6. Как путь превращается в адрес — пошагово

Возьмём `property_demo` (64 бита). Корень — `PointerPath(&g_World, {0})`, то
есть объект `*g_World`. Раскладка: `World.hero` по `0x10`, `Character.bag` по
`0x18`, `Inventory.items` по `0x10` (контейнер `{Item** data; int32 count}`,
`count` через 8 байт), элемент — указатель (шаг 8), `Item.quantity` по
`0x10`. Путь: `Hero.Bag.Items[1].Quantity`.

| Шаг | Действие | PointerPath после шага |
|---|---|---|
| 0 | Корень. Тип объекта не задан, поэтому путь разрешается: `*g_World`, оттуда указатель на тип, схема `World` | `[&g_World]` |
| 1 | `Hero`: нашли в схеме `World`, смещение `0x10` → `Offset(0x10)` | `[&g_World]+0x10` |
| 2 | `Hero` — `StructPointer` и не последний → `Dereference()`; тип берётся по фактическому объекту героя: `Character` | `[[&g_World]+0x10]` |
| 3 | `Bag`: смещение `0x18` → `Offset(0x18)`; указатель → `Dereference()`; тип `Inventory` | `[[[&g_World]+0x10]+0x18]` |
| 4 | `Items`: смещение `0x10` → `Offset(0x10)` | `[[[&g_World]+0x10]+0x18]+0x10` |
| 5 | `[1]`: массив динамический, поэтому путь до контейнера **разрешается**, и `count` (= 2) читается по `+8`. Индекс 1 < 2 — можно. Затем `Dereference()` (данные — первое поле) и `Offset(1 × 8)` | `[[[[&g_World]+0x10]+0x18]+0x10]+0x8` |
| 6 | Элемент — `StructPointer` и не последний → `Dereference()`; фактический тип элемента: `Item` | `[[[[[&g_World]+0x10]+0x18]+0x10]+0x8]` |
| 7 | `Quantity`: смещение `0x10`. Последний сегмент — путь готов | `[[[[[&g_World]+0x10]+0x18]+0x10]+0x8]+0x10` |

Именно эту строку печатает `property_demo` (`location->path.ToString()`).
Затем `Read()` разрешает путь (`ResolveTraced`) и читает 4 байта как
`Int32`.

Правила выбора типа вложенного объекта (`StructPointer`):

1. задан `struct_type` — берётся статическая схема с этим именем;
2. иначе, если настроена рефлексия, тип читается **из самого объекта**.
   Поэтому у наследника доступны его собственные свойства (в тестах
   `Items[1]` — наследник `Potion` со свойством `Potency`);
3. иначе, если известен `struct_type_object`, используется объявленный тип;
4. иначе — ошибка `UnknownType`.

Для вложенной структуры по значению (`Struct`) действуют правила 1 и 3:
своего указателя на тип у неё нет.

Индексы проверяются так: у inline-массива — по `inline_count`, у
динамического — по `count` в памяти. Если `count` больше `max_count`
(2²⁰), это `ValueOutOfRange`: в памяти мусор.

### 8.7. Get&lt;T&gt;: правила преобразования

| Запрошенный `T` | Принимает | Иначе |
|---|---|---|
| `bool` | только `bool` | `TypeMismatch` |
| целые (`int`, `uint8_t`, `int64_t`…) | целые, **если значение помещается в `T`** | `ValueOutOfRange` (например, 300 в `uint8_t`, −3 в `unsigned`) или `TypeMismatch` (вещественное, строка) |
| `float`, `double` | вещественные и целые | `TypeMismatch` |
| `std::string` | только строки (`String`, `Name`) | `TypeMismatch` |
| `Address` | только адреса (`Pointer`, `StructPointer`, `Struct`, `Array`) | `TypeMismatch` |
| `PropertyValue` | всё | — |

То же преобразование доступно отдельно: `ConvertValue<T>(value)`.

### 8.8. Result и коды ошибок

Методы не бросают исключений, а возвращают `Result<T>`, аналог
`std::expected` из C++23:

```cpp
auto hp = fetcher.Get<int>(hero, "Health");
if (hp) use(*hp);
else log(memrefl::FetchErrorCodeName(hp.error().code), hp.error().message);
int value = hp.value_or(0);
```

* `ok()` / `operator bool` — есть ли значение;
* `*r`, `r->`, `r.value()` — значение; `value()` на ошибке бросает
  `BadResultAccess` с текстом ошибки;
* `value_or(x)`, `error().code`, `error().message`;
* у временного `Result` значение отдаётся по значению, поэтому
  `for (auto& e : fetcher.Dump(obj).value())` безопасен.

| Код | Когда |
|---|---|
| `InvalidPath` | Синтаксис пути; поле у скаляра (`Health.Value`); индекс у не-массива |
| `UnknownType` | Нет схемы с таким именем; тип объекта не задан, а рефлексия не настроена |
| `UnknownProperty` | Нет такого свойства. Сообщение подсказывает ближайшее имя: `did you mean 'Health'?` (расстояние Левенштейна ≤ max(1, длина/3)) |
| `NullPointer` | На пути встретился нулевой указатель; в сообщении — путь и номер шага |
| `UnreadableMemory` | Память недоступна; строку или метаданные не удалось прочитать |
| `IndexOutOfRange` | Индекс ≥ длины массива (`count is 2`) |
| `ValueOutOfRange` | Значение не помещается в `T`; мусорная длина массива |
| `TypeMismatch` | `Get<T>` с несовместимым `T`; `Count` у не-массива |
| `UnsupportedType` | Тип `Unknown`; массив массивов; нет нужного resolver'а; не задан `stride` |
| `NameUnresolved` | ID имени нет в таблице (в сообщении — `<unknown:0x…>`) |

### 8.9. Остальные методы

| Метод | Что делает |
|---|---|
| `Fetch(obj, path)` | `Result<PropertyValue>` |
| `Locate(obj, path)` | `PropertyLocation{path (PointerPath), property (описание значения), owner_type}` без чтения значения |
| `Read(location)` | Перечитать значение по готовому пути. Разбор строки и поиск по схемам не повторяются, поэтому это удобно для частого опроса |
| `Count(obj, array_path)` | Длина массива |
| `TypeName(obj)` | Имя типа (из `ObjectRef` или из метаданных) |
| `Dump(obj)` | Все свойства со значениями, родительские первыми. Ошибка одного свойства не прерывает выгрузку |

`ObjectRef{root, type}`: `root` — адрес (`ObjectRef{0x1234, "Character"}`)
или `PointerPath` (`ObjectRef{PointerPath(&g_World, {0})}`); `type` — имя
статической схемы. Пустой `type` означает, что тип нужно взять из памяти.

`FetcherOptions::pointer_size` — ширина указателей цели (4 для 32-битной).

**Настройка и потоки.** `SetNameResolver(resolver, key)` и
`SetReflection(loader)` вызываются до использования. После этого
константные методы можно вызывать из нескольких потоков (проверено под
ThreadSanitizer).

## 9. Всё вместе: разбор property_demo шаг за шагом

Файл `examples/property_demo.cpp` состоит из двух частей.

**«Приложение»** (`namespace app`) устроено как типичная программа с рефлексией:

* `g_Names` — таблица имён; объекты и метаданные хранят только индексы в ней;
* `TypeInfo {name; super*; first*}` и `PropInfo {name; offset; tag; inner*; next*}` —
  описания типов `Object`, `Item`, `Inventory`, `Character`, `World`;
* у каждого объекта первым полем идёт `const TypeInfo* type`;
* корень данных — глобальная переменная `World* g_World`;
* `g_Code` — фрагмент машинного кода `48 8B 05 rel32 48 85 C0 74 05`
  (`mov rax, [rip + g_World]; test rax, rax; jz`). Настоящий компилятор
  сгенерировал бы его сам; здесь он собирается при старте, чтобы пример не
  зависел от компилятора.

**«Инструмент»** (`main`) не использует типы приложения, только адреса и раскладку:

1. **Модуль 1.** `SignatureScanner` по `g_Code` +
   `FindRelativeTarget(Pattern("48 8B 05 ?? ?? ?? ?? 48 85 C0 74 ??"), 3, 7)` →
   адрес `g_World`. Программа проверяет, что он совпал с настоящим. В
   реальном инструменте здесь был бы `ScannerForModule("app.exe")`; в
   примере сканируется только `g_Code`, чтобы такая же последовательность в
   коде самого примера не сделала сигнатуру неоднозначной.
2. **Модуль 2.** `ArrayTableSpec` над `g_Names` → `GenericDataResolver`.
   Чтение идёт через `ProcessMemoryReader::Self()`.
3. **Модуль 3.** `ReflectionLayout` заполняется через `offsetof` от
   `TypeInfo`/`PropInfo`; таблица тегов: 1 → Int32, 2 → Float, 3 → указатель
   на объект, 4 → динамический массив указателей, 5 → ID имени.
   `PropertyFetcher` получает загрузчик и resolver.
4. Корень — `PointerPath(&g_World, {0})`. Пример читает `Hero.DisplayName`
   (кириллица из таблицы имён), `Hero.Health`, `Hero.Bag.Items[1].Quantity`.
   Показаны три ошибки: выход за массив, опечатка с подсказкой, поле у
   скаляра. Затем `Count` и `Get<T>` с проверкой типа.
5. `Locate("Hero.Bag.Items[1].Quantity")` печатает путь. Приложение
   заменяет предмет и меняет здоровье, а `Read(location)` и повторный `Fetch`
   видят новые значения.
6. `Dump` героя: все свойства с типами, смещениями и значениями.

## 10. Как применить к новой программе

Общий порядок работы:

1. **Найдите корень данных.** Это глобальная переменная (менеджер, мир,
   реестр), от которой достижимы нужные объекты. В дизассемблере найдите
   инструкцию, которая к ней обращается, и составьте сигнатуру (раздел 6.9).
   Проверьте её: `FindUnique` должен находить ровно одно место.
2. **Найдите таблицу имён**, если программа хранит ID вместо строк.
   Определите её вид (массив, поблочный массив, хеш-таблица) и раскладку
   записи строки. Настройте `ArrayTableSpec`/`HashTableSpec` и проверьте
   через `ForEachName`: первые имена должны выглядеть осмысленно. Если ID —
   хеши строк, подберите алгоритм на известном имени (`HashString` с разными
   `StringHashOptions`) и используйте `DictionarySpec`.
3. **Опишите типы.**
   * Если в программе есть метаданные рефлексии, заполните `ReflectionLayout`
     и таблицу тегов. Проверяйте через `fetcher.Dump(ObjectRef{адрес})`:
     сразу видны все свойства и их значения, а неизвестные теги — как
     `Unknown`.
   * Если метаданных нет, опишите схемы вручную (`TypeSchema`). Начните с
     нескольких полей, значения которых знаете, и проверяйте их через
     `Dump`.
4. **Читайте значения** через `Get<T>`. Для частого опроса один раз вызовите
   `Locate` и затем `Read`.
5. **Обрабатывайте ошибки как обычную ситуацию:** объект может быть удалён,
   указатель пуст, ID без имени. `Result` и сообщения с путём делают это
   простым.
6. **После обновления программы** проверьте сигнатуры (`FindUnique`) и одно-два
   известных значения через `Dump`. Если сигнатура перестала находиться,
   обновите её. Смещения полей в схемах из метаданных обновятся сами.

## 12. Решение проблем

| Симптом | Вероятная причина | Что сделать |
|---|---|---|
| Ошибки компиляции около `min`/`max` в своих файлах | Макросы `<windows.h>` | В своём коде пишите `(std::min)(a, b)` или определите `NOMINMAX` до `<windows.h>`. Заголовки memrefl от этого защищены |
| Предупреждения C4819 в MSVC | Заголовки в UTF-8, а компилятор читает их в кодировке системы | Добавьте флаг `/utf-8` |
| Кракозябры вместо кириллицы в консоли | Консоль не в UTF-8 | `SetConsoleOutputCP(CP_UTF8)` (примеры делают это сами), Windows Terminal или `chcp 65001` |
| `FindUnique` вернул `nullopt` | Сигнатуры нет (код изменился) или она неоднозначна | `FindAll(p, 10)`: 0 совпадений — обновите сигнатуру; несколько — удлините её или добавьте соседние инструкции |
| `ScannerForModule` пуст | Неверное имя модуля | Windows: имя файла с расширением (`app.exe`, `engine.dll`); Linux: имя файла (`libfoo.so`) или полный путь; `""` — главный модуль |
| `ProcessMemoryReader` для другого процесса ничего не читает | Нет прав | Windows: `OpenProcess` с `PROCESS_VM_READ`, при необходимости запуск от администратора. Linux: тот же пользователь и `ptrace_scope` = 0, либо `CAP_SYS_PTRACE` |
| Строки читаются «мусором» | Неверная кодировка или раскладка записи | Попробуйте `Utf16LE` или `Latin1`; проверьте `chars_offset`, `chars_by_pointer`, поле длины |
| Имена `<unknown:0x…>` | ID не в таблице или неверный конвертер | Проверьте `KeyConverter` (флаги, нумерация с 1) и границу `count`; выгрузите таблицу через `ForEachName` |
| `UnknownProperty` для существующего поля | Имя в схеме записано иначе; объект другого типа | Посмотрите `Dump(obj)` и `TypeName(obj)`: там видны все имена |
| `NullPointer` в середине пути | Объект ещё не создан или уже удалён | Это нормальная ситуация в живом процессе; сообщение показывает, на каком шаге |
| Значения «съехали» на несколько байт | Неверные смещения или ширина указателей | Для 32-битной цели задайте `pointer_size = 4` в fetcher, layout и specs |
| `ValueOutOfRange` у массива | `count` в памяти мусорный | Проверьте `count_offset`/`count_size`; при большой нормальной длине увеличьте `max_count` |
| `Read()` по сохранённому пути вернул старый индекс | Массив укоротился после `Locate` | Перед `Read` проверяйте `Count` или вызывайте `Locate` заново |

## 13. Ограничения

* **Только чтение.** Библиотека не изменяет память цели.
* Раскладку (смещения, теги, формат контейнеров) нужно знать заранее. Её
  находят при исследовании программы; модуль 1 помогает найти адреса, а
  метаданные рефлексии (если они есть) дают смещения автоматически.
* `ResolveRelative` рассчитан на 32-битные относительные смещения
  (x86/x86-64).
* Модули и память текущего процесса поддерживаются на Windows и Linux. Поиск
  в буферах, разбор PE, таблицы и схемы работают на любой little-endian
  платформе.
* Динамический массив описывается как `{T* data; …; count}` с данными в
  первом поле. Массивы массивов не поддерживаются. Другие контейнеры можно
  описать через `Pointer` и ручной `PointerPath`.
* Чтение живого процесса не атомарно: пока читается сложная структура,
  программа может её менять. Защита от мусора и циклов гарантирует только
  отсутствие падений и зависаний, но не согласованность снимка.
* `ProcessMemoryReader` делает системный вызов на каждое чтение. Для
  многократного разбора больших таблиц выгоднее один раз снять
  `ExportDictionary()` или читать снимок через `RegionReader`.
* Для схем из метаданных `owner_type` — тип объекта, а не родитель, где
  свойство объявлено: родительские свойства копируются в схему потомка.
* Сборка в MSVC не проверялась (раздел 3). После сборки запустите `ctest`.
